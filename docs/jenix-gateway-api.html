Jenix Lock Gateway API

The Jenix Lock Gateway is a Wi-Fi bridge that lets your software control Jenix / HAHA Bluetooth smart locks over a simple, authenticated HTTP API. Your application talks to the gateway on the local network (or through your own cloud); the gateway handles all Bluetooth communication with the locks. One gateway can manage several locks.

Transport: HTTP/JSON over Wi-Fi (LAN) Auth: Bearer token Hardware: ESP32-S3 Optional cloud: MQTT Multi-lock per gateway

How it works

Your software never speaks Bluetooth. It sends normal HTTP requests to the gateway; the gateway keeps a secure session to each lock and translates your commands into the lock's native BLE protocol.

Your software
web, mobile, server or PLC
→HTTP / JSON
Jenix Gateway
ESP32-S3 on Wi-Fi
→Bluetooth LE
Smart lock(s)
Jenix / HAHA
No-RTC locks. The locks have no real-time clock, so their time resets after a battery change. The gateway synchronises time automatically over NTP on first connect and after a battery recovery — your software does not need to manage lock time, though POST /api/time is available.

Quick start

Every request (except /api/health) carries the gateway's API token. Replace <gateway-ip> with the gateway's address on your network and <API_TOKEN> with its token (printed on the gateway's serial console and shown in the Jenix Lock app).

# 1. Is the gateway up? (no auth)
curl http://<gateway-ip>/api/health

# 2. List the locks this gateway manages
curl -H "Authorization: Bearer <API_TOKEN>" \
     http://<gateway-ip>/api/locks

# 3. Unlock a lock
curl -X POST -H "Authorization: Bearer <API_TOKEN>" \
     -H "Content-Type: application/json" \
     -d '{"user":1,"pin":"135790"}' \
     "http://<gateway-ip>/api/unlock?lock=<lock-id>"

Base URL & authentication

ItemValue
Base URLhttp://<gateway-ip>  (plain HTTP on the LAN; discoverable at jenixlock-xxxx.local via mDNS, or by probing /api/health for its device_id)
Auth headerAuthorization: Bearer <API_TOKEN> on every endpoint except GET /api/health
Request bodyJSON, with Content-Type: application/json on POST requests that take a body
ResponseJSON, always including a boolean ok field
Keep the token secret. It grants full control of every lock on the gateway. Treat it like a password: store it server-side, never embed it in a public web page or mobile binary you cannot control. Rotate it by factory-resetting the gateway if it is exposed.
Wi-Fi extenders / repeaters. Many consumer repeaters that re-broadcast the router's network name block traffic between their clients and the main router's clients. If the gateway and your client join different access points, requests time out although the gateway is online. GET /api/health reports the gateway's access point (wifi_bssid, wifi_channel, wifi_rssi) to help diagnose this. Use one router, a proper mesh system, or give the repeater its own network name.

Selecting a lock

A gateway can hold several locks, so operation endpoints need to know which one. You can specify the lock in either of two ways:

MethodExample
Query string (works for GET and POST)POST /api/unlock?lock=8F3EE684ECE3
Body field (POST only){"lock":"8F3EE684ECE3","user":1,"pin":"1234"}

If the gateway has exactly one bound lock, you may omit the selector entirely and it will be used by default. The lock value is the lock's ID as returned by GET /api/locks.

Responses & errors

Success responses return HTTP 200 with "ok": true and any result fields. Failures return an HTTP error status with a machine-readable envelope:

{ "ok": false, "error": "lock not bound: 8F3EE684ECE3" }
StatusMeaning
200Success (ok: true).
400Bad request — malformed JSON or a missing/invalid field.
401Missing or wrong bearer token.
404Unknown endpoint, or lock not found for an unbind.
502The lock could not be reached or the BLE operation failed — see below.

Reachability — did the command reach the lock?

Guaranteed delivery semantics. Before every command the gateway checks that the lock is advertising and within signal range. If the lock is out of range, asleep, or the signal is too weak, the gateway returns 502 with a clear message and does not send the command. A 200 / ok:true therefore means the command actually reached the lock — your software never has to guess.
// weak signal — command was NOT sent
{ "ok":false, "error":"lock not reachable: weak signal (RSSI -94 dBm, need >= -92); command NOT sent" }
// lock not advertising (out of range or asleep)
{ "ok":false, "error":"lock not reachable: not advertising (out of range or asleep)" }

GET/api/locksBearer

List the locks bound to this gateway. Passwords are never returned.

Response
{
  "ok": true,
  "locks": [
    { "lock_id": "8F3EE684ECE3", "tz_minutes": 330 }
  ]

GET/api/scanBearer

Scan for Jenix/HAHA locks advertising near the gateway (about 4 s). Locks advertise as Lck1_<ID>; bind with the bare ID after the underscore (e.g. Lck1_8F3EE684ECE3 → 8F3EE684ECE3) — the ID is part of the login key.

Response
{

Binding locks

Binding stores the lock's BLE password in the gateway so it can open a session later; the password is sent only once and never returned.

POST/api/bindBearer

Bind a lock to the gateway. Two cases:

  • Lock already set up (has a connection password): send that password. It is the 6-digit connection password chosen when the lock was first added — not a keypad PIN.
  • New or factory-reset lock: add "set_password": true and the gateway sets your chosen password on the lock itself (lock must be awake and in range).
Request body
{
  "lock_id": "8F3EE684ECE3",   // required — bare ID (no "Lck1_")
  "password": "123456",        // required — 6-digit connection password
  "tz_minutes": 330,           // optional — minutes east of UTC (IST = 330)
  "set_password": false        // true = new/reset lock: set this password on it
}
Binding only stores the password. Call GET /api/version?lock=… right after to prove it: 502 "login error 19" (or 33) means the password is wrong — unbind and try again. "login error -1" means the lock did not answer (asleep): retry after touching its keypad. With set_password, 409 means the lock is already set up and the existing password is needed.
Response
{ "ok": true, "lock_id": "8F3EE684ECE3" }
POST/api/unbindBearer

Remove a lock from the gateway.

Request body
{ "lock_id": "8F3EE684ECE3" }
Response
{ "ok": true }   // 404 if the lock was not bound

Lock operations

All operation endpoints accept ?lock=<lock_id> (or a "lock" body field), defaulting to the only bound lock.

POST/api/unlockBearer

Open the lock. user and pin identify an authorised user on the lock. If gateway auto close is set for this lock (see settings), the gateway locks it again after that many seconds with the same user and PIN, and reports the countdown.

Request body
{ "user": 1, "pin": "135790" }
Response
{ "ok": true, "auto_close_in": 10 }   // auto_close_in only when gateway auto close is on
502 "unlock rejected" = the lock refused this user ID + PIN combination (wrong PIN or user).
POST/api/lockBearer

Close / re-lock. Same body as unlock.

{ "user": 1, "pin": "135790" }  // -> { "ok": true }
GET/api/versionBearer
Response
{
  "ok": true,
  "firmware": "BK50D-V2.5",
  "command_version": 0,   // 0 = supported login protocol
  "admin_exists": true
}
GET/api/batteryBearer
Response
{ "ok": true, "percent": 100, "voltage": 5.7 }
GET/api/timeBearer

Read the lock's clock.

{ "ok": true, "time": "2026-11-25 17:04:39" }

Set the lock's clock. Send an explicit time, or send an empty body to use the gateway's NTP time.

Request body (all fields optional)

Credential enrollment

Enroll a fingerprint, card or PIN for an existing user. Fingerprint and card capture happen at the lock, so your software starts enrollment and then polls for status; PIN is set in one call.

POST/api/enrollBearer

Begin enrollment for a user.

Request body
{
  "type": 1,       // 1 = fingerprint, 2 = PIN, 3 = card
  "user": 2,       // target user id
  "pin": "4821"    // required only for type 2 (PIN)
}
Response
{ "ok": true, "poll": true }   // poll:true -> keep calling /api/enroll/status
PINs must be unique on a lock. Setting or changing a PIN to a value another user already has returns 409 "this PIN can't be used - please choose a different PIN" (lock error 26); the user keeps their current PIN. Do not tell end users the reason — "already used by another user" would let someone discover other users' PINs by trial. Changing an existing user's PIN to a new, unique value works directly with type: 2.
GET/api/enroll/statusBearer

Poll fingerprint/card capture progress (e.g. every second) until done is true. The lock reports "idle" before the person presents a finger/card too, so done only becomes true after the lock has shown activity. Give up after ~60 s and call cancel.

{
  "ok": true, "status": 0, "payload_len": 1,
  "phase": "done",   // waiting | capturing | progress | waiting_card | card_read | done
  "done": true
}
POST/api/enroll/cancelBearer

Abort an in-progress enrollment. Empty body. -> { "ok": true }

Access records

GET/api/records?days=NBearer

Access log for the last N days (default 7), newest first, in the lock's local time. It merges two sources: the lock's own memory (fingerprint, card and PIN opens at the keypad) and the gateway's log of every lock/unlock it sent (app, cloud, auto close) — the lock itself does not record those.

If the lock is asleep, the response still returns the gateway's entries with "lock_unreachable": true.
Response
{
  "ok": true,
  "count": 2,
  "records": [
    { "user": 2, "time": "2026-11-25 09:14:02", "mode": "fingerprint",
      "source": "lock", "action": "unlock", "ok": true, "mode_byte": 1, "direction": 0 },
    { "user": 1, "time": "2026-11-25 09:20:40", "mode": "app",
      "source": "app", "action": "unlock", "ok": true }
  ]
}
// mode:   fingerprint | card | pin | other (lock)  ·  app | cloud | auto | serial (gateway)
// action: unlock | lock     ok: false = the lock refused the command

Lock settings

GET/api/settingsBearer

Current lock settings: the lock's own auto-lock delay, the gateway auto close for this lock, and the normally-open schedule.

Response
{
  "ok": true,
  "auto_lock_s": 5,          // lock's own re-lock delay
  "app_auto_close_s": 10,    // gateway re-locks 10 s after app/cloud unlocks (0 = off)
  "normally_open": { "enabled": false, "start_minute": 0, "end_minute": 0, "weekday_mask": 0 }
}
POST/api/settings/autolockBearer

The lock's own re-lock delay, 3–60 seconds. Applies to every kind of opening. Locks fitted with a door sensor (magnet) re-lock only after the sensor sees the door closed — without the magnet they stay open; use gateway auto close below for app openings.

{ "seconds": 5 }   // -> { "ok": true }
POST/api/settings/app-autocloseBearer

Gateway auto close: after an unlock made through the gateway (API, app, cloud) the gateway sends the lock command itself after this delay — works without a door magnet. 0 turns it off. Keypad / fingerprint / card openings do not pass through the gateway, so they rely on the lock's own auto-lock.

Request body
{ "seconds": 10 }   // 0 = off, or 3–300
Response
{ "ok": true, "app_auto_close_s": 10 }
POST/api/settings/normally-openBearer

Keep the lock open during a daily window (e.g. business hours). Minutes are from midnight; the weekday mask is a bitmask of the days the window applies. Send {"enabled": false} to turn the schedule off. While the window is active the door is unlocked and auto-lock does not act (press and hold 0 on the keypad to lock manually).

Request body
{
  "weekday_mask": 127,    // bit0=Sun … bit6=Sat; 127 = every day
  "start_minute": 540,    // 09:00
  "end_minute": 1080      // 18:00
}
// turn off: { "enabled": false }
Response
{ "ok": true }
POST/api/settings/factory-resetBearer

Erase all users and settings on the lock and unbind it from the gateway. Irreversible — requires an explicit confirmation token.

Request body
{ "confirm": "RESET" }   // exact string required, else 400
Response
{ "ok": true }

Battery alerts

The gateway measures every bound lock's battery itself — 2 minutes after start-up, then every 6 hours (one short Bluetooth session per lock). Poll this from your software or app to warn users before the batteries run out.

GET/api/alertsBearer

Last measured battery per bound lock. low is true below the threshold (25 %). battery is -1 until the first measurement.

Response
{
  "ok": true,
  "threshold": 25,
  "locks": [
    { "lock_id": "8F3EE684ECE3", "battery": 18, "voltage": 4.6, "checked_at": 1795680000, "low": true }
  ]
}
POST/api/alerts/checkBearer

Measure every lock now (about 2–10 s per lock). Returns the same shape as GET /api/alerts.

Request body
{}

Signal & diagnostics

GET/api/signal?lock=…Bearer

Live signal of the gateway–lock Bluetooth link (connects if needed; no command is sent) and the gateway’s Wi-Fi signal. Keeping the link open uses the lock’s battery — poll for a minute at most.

Response
{ "ok": true, "connected": true, "ble_rssi": -58, "wifi_rssi": -49, "min_rssi": -92 }
// > -65 excellent · -65..-75 good · -75..-85 fair · below -85 weak
GET/api/probe?lock=…Bearer

Read a lock’s model and login protocol without logging in — useful before binding an unknown lock. supported is false for locks using a newer login protocol.

Response
{ "ok": true, "firmware": "BK21F-V2.6.1", "command_version": 0, "supported": true,
  "admin_exists": false, "rssi": -71, "bound_here": false }
GET/api/radioBearer

Gateway transmit power. POST the same fields to change it: Wi-Fi 8/11/13/15 dBm, Bluetooth 0–15 dBm in steps of 3. Higher power needs a solid 5 V / 2 A supply; after a power dip the gateway steps the power back down by itself (stepped_down).

Response
{ "ok": true, "wifi_dbm": 11, "ble_dbm": 9, "wifi_rssi": -48, "stepped_down": false }

Temporary door codes (offline, one-time)

A visitor can open the lock with a 6-digit code typed on the keypad. The code is computed by your software (no gateway or network call); the lock computes the same value from its own clock and accepts it during the current 5-minute window. The Jenix Lock app does exactly this on its Control tab.

Always use the lock's keypad ADMIN PIN to generate codes — the PIN the lock's admin user types on the keypad. It is not the 6-digit connection password used for /api/bind, and not a general user's PIN. With any other value the codes look valid but the lock rejects them. (Live-confirmed: the connection password produced a correct-looking code the lock refused; the admin PIN opened it.) A lock with no admin user cannot accept temporary codes.

Algorithm (KG5)

  1. Take the lock's local time — current UTC plus the lock's time zone (tz_minutes, 330 for India). Do not use the phone's or server's local time zone.
  2. Format it as yyMMddHHmm and round the last minute digit down to 0 or 5 (e.g. 09:07 → 2601150905).
  3. Append 000000 and read the 16 digits as 8 hex bytes (26 01 15 09 05 00 00 00).
  4. Key = the admin PIN as ASCII, padded with spaces / cut to 8 characters.
  5. Encrypt the block with single DES-ECB using that key → 8 bytes c[0..7].
  6. Code = ((c[5] & 0x0F) << 16 | c[6] << 8 | c[7]) mod 1 000 000, zero-padded to 6 digits.
Test vector
// admin PIN "246810", lock local time 2026-01-15 09:07 (window 09:05-09:10)
block 2601150905000000  key "246810  "  →  code 961012

Using a code

Touch the keypad to wake it, press *, enter the 6-digit code, then press #. Codes are valid only for their 5-minute window, so show the window (e.g. "valid 09:05–09:10") when you share one. The gateway keeps the lock clock on NTP time, which these codes depend on.

Cloud connectivity (MQTT)

For control from outside the LAN, the gateway can connect out to an MQTT broker you run (your VPS/cloud). It publishes status and heartbeats and accepts commands — so your cloud software can reach locks without any inbound port on the customer's network.

GET/api/cloudBearer
Response
{
  "ok": true,
  "enabled": true,
  "host": "mqtt.example.com",
  "port": 1883,
  "client_id": "gw-001",
  "connected": true   // password is never returned
}
POST/api/cloudBearer

Configure the broker. Any omitted field is left unchanged.

Request body
{
  "enabled": true,
  "host": "mqtt.example.com",
  "port": 1883,
  "client_id": "gw-001",
  "user": "gateway",
  "pass": "••••••"
}
Response
{ "ok": true }

MQTT topics

<id> is the configured client_id (or the device MAC if unset).

TopicDirPurpose
jenix/<id>/statusgateway → cloudRetained online/offline status (offline via MQTT Last-Will).
jenix/<id>/heartbeatgateway → cloudPublished every 30 s.
jenix/<id>/cmdcloud → gatewayCommand requests (status / unlock / lock / battery).
jenix/<id>/respgateway → cloudCommand replies.
The broker and your cloud application are yours to provide; the gateway is the MQTT client. For production, run the broker over TLS.

Firmware updates

Two ways to update the gateway. Either way, all saved configuration (Wi-Fi, API token, bound locks, cloud settings) is preserved, and GET /api/health reports the running fw_version afterwards.

POST/api/ota/uploadBearer

Upload a firmware file directly (multipart form, field firmware) — this is how the Jenix Lock app installs the firmware bundled inside each app release. Send header X-MD5 (hex) to have the image verified before it is activated. A wrong, partial or corrupted file is rejected and the running firmware stays in place. Requires gateway firmware 1.2.0 or newer.

Example
curl -H "Authorization: Bearer <API_TOKEN>" -H "X-MD5: <md5-hex>" \
     -F "firmware=@jenix-gateway.bin" http://<gateway-ip>/api/ota/upload
Response
{ "ok": true, "message": "firmware installed; the gateway restarts now" }
// then poll GET /api/health until "fw_version" shows the new version
POST/api/otaBearer

Or let the gateway pull a .bin from a URL you host (LAN or VPS, plain http). The gateway downloads, flashes the application partition, and reboots on success. All saved configuration (Wi-Fi, API token, bound locks, cloud settings) is preserved.

Request body
{ "url": "http://downloads.example.com/jenix-gateway-1.2.5.bin" }
Response
{ "ok": true, "message": "downloading firmware; the gateway will reboot on success" }

LAN updates are also available over standard ArduinoOTA (espota), using the API token as the OTA password.

Wi-Fi provisioning

On first power-up (or after a field reset) the gateway starts its own access point JenixLock-XXXX at 192.168.4.1. A client joined to it provisions the home Wi-Fi with the calls below; no token is needed while the gateway is factory-fresh (/api/health returns "setup": true), and the reply carries the gateway's API token. Once Wi-Fi is saved, these calls require the bearer token.

GET/api/wifi/scanSetup

Nearby Wi-Fi networks, strongest first (2.4 GHz only).

{ "ok": true, "networks": [ { "ssid": "MyNetwork", "rssi": -52, "secure": true } ] }
POST/api/provisionSetup
{ "ssid": "MyNetwork", "pass": "MyPassword" }
Response
{ "ok": true, "device_id": "<12 hex>", "token": "<api-token>", "hostname": "jenixlock-xxxx.local" }

The gateway joins the network while keeping its access point up, and saves the credentials only if the join succeeds.

GET/api/provision/statusOpen

Poll every 1–2 s. state is connecting, connected (with the new LAN ip) or failed (with error).

{ "ok": true, "state": "connected", "ip": "192.168.1.50", "device_id": "<12 hex>" }
POST/api/provision/finishBearer

Closes the setup access point (it otherwise closes 3 minutes after joining). Then reconnect the client to the home Wi-Fi and reach the gateway at the reported IP. If the IP later changes, find the gateway again by probing GET /api/health on the subnet for the same device_id.

POST/api/wifiSetup

Browser fallback: form-encoded (application/x-www-form-urlencoded), used by the setup page at http://192.168.4.1/.

ssid=MyNetwork&pass=MyPassword
To reset a gateway in the field, press its onboard RESET button ~10 times — this clears its own configuration (Wi-Fi, token, bound locks) and returns it to setup mode. It never affects the locks' data.

Integration notes

Server-side or mobile

Call the API from your backend, a mobile app, or an on-site controller on the same Wi-Fi. These clients are not subject to browser CORS. This is the recommended integration path.

Browser / web page

A web page in a browser calling the gateway directly is subject to CORS. The gateway firmware can enable permissive CORS headers on request — ask Jenix to enable it for a browser-based integration, or proxy the calls through your own server.

One gateway, many locks

Scale by binding multiple locks to a gateway and selecting with ?lock=, or deploy multiple gateways. Each gateway has its own IP and token.

Reliability

The gateway is built for 24×7 unattended operation: software watchdog, Wi-Fi auto-reconnect, brownout protection, and all state in non-volatile memory, so it recovers from any reset in seconds.
